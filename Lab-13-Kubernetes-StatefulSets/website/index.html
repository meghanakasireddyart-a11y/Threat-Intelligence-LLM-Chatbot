🧱 The BSON Document Constraint

Activity 7.1

In MongoDB, embedding provides atomic updates and single-seek reads. However, storing unbounded arrays within a document is an anti-pattern that leads to severe production vulnerabilities:

  • Hard Limit Failure: Any document exceeding 16MB triggers BSONObjectTooLarge (error 10334) and rejects further writes.
  • Memory Thrashing: WiredTiger must read the entire document into cache even when the application only needs the blog post title.
  • Reallocation Overhead: Array growth via $push requires contiguous memory reallocations, creating fragmentations and write latency spikes.

⚡ WiredTiger Working Set Architecture

Activity 7.2

WiredTiger uses an internal LRU (Least Recently Used) cache to maintain active pages in uncompressed memory:

  • Working Set ≤ Cache: 100% cache hits, near-zero disk I/O, sub-millisecond query responses.
  • Working Set > Cache: Application threads get drafted into performing disk evictions (eviction pages evicted by application threads), causing query latency to spike from milliseconds to seconds.
  • Sequential Inserts: Recently inserted records remain resident in cache; older pages are evicted first under memory pressure.

🔍 The Core Prediction Question Answered

Prompt Question: "Predict whether all three ranges will take roughly the same amount of time, or whether some will be noticeably slower -- and say which range you expect to be slowest and why."

Under Memory-Constrained Production (Working Set > Cache):

The Beginning range (0-1,000) is the slowest. Because documents are inserted sequentially from 0 to 100,000, documents 0-1,000 were written first and represent the oldest pages in the WiredTiger cache. As the 100,000 inserts progress, earlier pages are LRU-evicted to disk. Querying 0-1,000 incurs cold disk read latency. The End range (99,000-100,000) is fastest because it is the most recently written and remains hot in RAM.

In This Exact Lab Environment (Cache = 7.8 GB, Data = 200 MB):

Because total data size (200MB) is a fraction of the available 7.8GB cache, all documents remain 100% memory-resident. Minor timing variations are caused by CPU thread scheduling, GC passes, and full COLLSCAN regex evaluations rather than disk eviction faults.

❓ Core Lab Questions & Detailed Technical Solutions

Q1: At what comment-count-per-post would a single blog post's embedded design approach or exceed the 16MB limit?

Mathematical Derivation:

The BSON specification imposes overhead for each embedded subdocument:

  • Base document header, title, author, slug, tags: ~180 bytes.
  • Each comment subdocument: 4 bytes (subdoc length) + 1 byte (string type) + 7 bytes (field author\0) + 14 bytes (string data) + 1 byte (string type) + 5 bytes (field text\0) + comment text bytes + 1 byte (date/string) + 24 bytes (timestamp) + 1 byte (subdoc terminator 0x00) = 63 bytes overhead + text length.
  • Array index keys ("0", "1", ... "10000"): 3 to 7 bytes per entry.

With an average realistic comment length of 300 bytes:
Average bytes per comment = 63 + 300 + 5 = 368 bytes
Comments to reach 16MB = (16 × 1024 × 1024) / 368 ≈ 45,590 comments.

With shorter comments (~150 bytes), it exceeds 16MB at ~75,000 comments. With rich comments or replies (~800 bytes), it fails at ~18,000 comments.
Warning Threshold: In production, any document exceeding 4MB to 8MB is already a severe performance hazard because reading or writing it saturates cache pages and networks.

Q2: Is "embed all comments in the post document" a safe design for this blog workload?

Verdict: UNSAFE. It is a textbook example of the Unbounded Array Anti-Pattern.

While the seed data has only 1 to 3 comments per post (~300 bytes total), in a production blogging system popular articles attract viral spikes with thousands of comments. The embedded design suffers from three fatal architectural flaws:

  1. Hard Ceiling Crash: Once comment count exceeds ~50k, MongoDB aborts writes with BSONObjectTooLarge. Users can no longer comment, and editors cannot edit the post.
  2. Read Amplification: Rendering an article list or post title forces MongoDB to transfer the entire multi-megabyte comments array over the wire, destroying API latency.
  3. Memory Fragmentation: Repeated $push operations to an embedded array exceed the document's pre-allocated memory chunk, forcing WiredTiger to continuously move and re-write the document on disk and in cache.

The Production Fix: Implement the Subset Pattern (embed only the 5 most recent comments in the post) combined with the Bucket Pattern (group historical comments into separate documents of 50 comments each in a comments collection).

Q3: Prediction & Explanation of Query Latencies Across Collection Ranges

Key Architectural Dynamics:

  • LRU Eviction Priority: Because documents are inserted sequentially, documents 0-1,000 are the oldest pages in memory. Under cache pressure, WiredTiger evicts them first. Documents 99,000-100,000 were written last and remain warm in cache. Hence in a constrained environment, Range 1 is slowest and Range 3 is fastest.
  • COLLSCAN Bottleneck: Because no index was created on sensor, every range query must scan 100% of documents. Adding db.working_set_docs.createIndex({"sensor": 1}) reduces scan from 100,000 docs to exactly 1,001 index keys, dropping query execution from ~200ms to <1ms.

🔬 Activity 11.1: MongoDB 5.0+ Resharding — Research Notes

Try It Yourself

MongoDB 5.0 introduced online resharding — the ability to change a collection's shard key without downtime, manual dump/restore, or application interruption.

📋 Resharding Steps

  1. Confirm MongoDB 5.0+ and Atlas or self-hosted replica set.
  2. Run db.adminCommand({ reshardCollection: "<db.coll>", key: { <newKey>: "hashed" } }).
  3. mongos starts a background clone of all documents to new chunks.
  4. The currentOp() command reports resharding progress (remainingOperationTimeEstimatedSecs).
  5. When cloning completes, a brief write-blocking "commit" window applies (typically < 2 seconds).
  6. Old chunk layout is replaced atomically; application sees no downtime.

⚠️ Resharding Limitations

  • Cannot reshard a time series collection or views.
  • Collection must have no active DDL operations during resharding.
  • Approximately 2× storage overhead during the clone phase (old + new data coexists).
  • Write throughput on the collection is reduced ~30% during the clone window.
  • Resharding cannot be used to change the key to/from _id.
  • Only one resharding operation per cluster at a time.
  • On Atlas, requires at minimum an M30 cluster tier.
💡
Monitor with: db.getSiblingDB("admin").currentOp({ type: "op", "$or": [{"desc": /reshard/i}] }) — shows real-time resharding progress, estimated completion time, and bytes cloned.

📦 StatefulSet vs Deployment

StatefulSets give each Pod a stable, unique network identity (mongo-0, mongo-1, mongo-2) and an ordered startup sequence—essential for replica set initialisation where the primary must be elected before secondaries join.

🌐 Headless Service (clusterIP: None)

A headless service with clusterIP: None creates individual DNS records per Pod (mongo-0.mongo.default.svc) instead of a single VIP, letting replica-set members address each other directly by stable hostname.

💾 volumeClaimTemplates

volumeClaimTemplates automatically provisions a dedicated PersistentVolumeClaim for each Pod so that Pod data survives rescheduling. Each node's data is isolated, preventing cross-node data corruption.

❓ What would break if serviceName references the wrong Service?

The StatefulSet's serviceName field controls what DNS suffix each Pod gets. If it references the wrong (or a non-headless) Service, the generated DNS records (mongo-0.<svc>.<ns>.svc.cluster.local) will not resolve, causing rs.initiate() to fail because the hostnames listed in the replica-set config cannot be reached by other members.
